# LLM и контракт команд

> Публичная копия: примеры подписок и регрессионные диалоги обезличены.
> Приведённые ниже SHA и результаты live eval — исторические результаты
> приватной разработки, а не измерения этой очищенной копии.

## Узкий интерфейс

IntentProvider.propose(message, received_at, timezone, context, candidate_records)
возвращает validated IntentEnvelope: query / proposed actions / clarification.
Provider не имеет подключения к БД, SQL, shell, произвольному HTTP или Telegram sender.
Реальный adapter использует структурированный output/tool arguments; Pydantic и
доменная проверка всё равно обязательны. FixtureProvider нужен с первого этапа.

Первый production adapter — OpenAI Responses API через AsyncOpenAI. Exact model ID
задаётся OPENAI_MODEL и выбирается после проверки доступа, качества и бюджета.
Не связывать выполнение с Claude Code subscription/session. Другой provider реализует
тот же интерфейс без переписывания БД. OpenAI key уже есть у пользователя; в cloud и
автоматических тестах использовать fixture, без ключа и платных вызовов.

## OpenAI transport contract

Один strict function tool propose_intent возвращает typed IntentEnvelope. Это предложение
команд, не прямой доступ к mutation. tool_choice задаёт propose_intent;
parallel_tool_calls=false; store=false; максимальный output и timeout ограничены.
Все JSON Schema object имеют additionalProperties=false; поля required, optional
значения выражены через null. Схему проверить против поддерживаемого subset OpenAI.
Не переносить параметры Chat Completions в Responses механически. Refusal, incomplete
и invalid/no tool call -> контролируемая ошибка, без мутации. Не использовать built-in
web/file/shell tools. Context хранится локально, без обязательного provider thread ID.
SDK retry policy согласовать с application retry: максимум один retry всего, без
двойного неограниченного повторения. store=false не обещает отсутствие всех provider logs.

## Команды application layer

create_task, update_task, complete_task, cancel_task;
create_obligation, update_obligation, mark_payment, extend_coverage;
record_topup, correct_balance, change_daily_rate;
snooze_notification, skip_occurrence, reschedule_occurrence, archive_obligation;
change_timezone, confirm_pending, cancel_pending;
query_agenda, query_payments, query_balance_forecasts, undo_command.
Каждая mutation имеет command_id, typed payload и expected_version когда обновляет
существующую запись. Время из модели — typed relative expression или явная дата, затем
deterministic resolver; не доверять произвольному computed timestamp.

Пример естественного ввода:
«Германию пополнил на тысячу, письмо отправил, Нидерланды больше не нужны».
Provider предлагает действия с candidate IDs. Последнее неоднозначно: архивировать
сервис или только пропустить пополнение? Создать pending intent/уточнение, показать
полный набор перед atomic commit. Ответ «да» действует только на актуальный pending
intent, не на произвольную прошлую реплику. Expiry default 30 минут.

## Pipeline

1. Authenticate owner; persist inbox and received_at; ограничить размер ввода.
2. Прямые кнопки/формы -> typed command без LLM. Свободный текст -> bounded context
   (последние 20 сообщений, максимум 12000 символов) + candidate search (до 30 записей).
3. Provider proposal; schema validation; dates/currency/object/version validation.
4. Clear single mutation -> apply. Bulk/destructive/ambiguous -> preview/clarification.
   Bulk = мутации двух и более разных предметов; считаются targets применяемых команд,
   а не упоминания в тексте. Несколько однозначных действий над одним предметом
   применяются сразу, кроме действий с отдельным подтверждением (архивация).
   Read-only запросы подтверждения не требуют. Неоднозначность дат («на следующей
   неделе» без дня) проверяет pipeline одинаково для любого provider.
5. Transaction writes data + receipt + audit + revised jobs.
6. Ответ успеха из committed result: названия, даты, суммы и следующий срок.

Не считать confidence score доказательством правильности. При двух похожих VPS
уточнить. «Все VPS» -> показать список и периоды, не включать произвольные сервисы.
Нет обязательства/платежа в БД -> честное отсутствие данных. Для писем «готово» в
контексте подготовки ответа может требовать уточнение отправки.

## Вопросы о платежах за период

QuerySpec передаёт не только kind, но и period/payment_status. Код вычисляет today,
tomorrow, this_week/next_week, this_month/next_month от времени исходного сообщения в
timezone пользователя. month принимает явно названный месяц и необязательный год;
range — только явно заданные даты. Начало/конец диапазона включены.
payment_status=unpaid выбирает открытые календарные периоды и предстоящие продления;
текущий оплаченный coverage не означает оплату следующего продления. Срок coverage —
последний оплаченный день. payment_status=paid показывает реальные Payment по paid_at,
а не по сроку продления. Отменённые оплаты не учитываются. Прогнозы balance помечаются
как оценки; неизвестные сроки не придумываются. Вопросы не меняют фактические записи.
Для payment_status=unpaid просроченное (открытый календарный период после срока,
закончившийся оплаченный период, расчётно исчерпанный баланс) показывается отдельным
блоком «Срок прошёл, отметки оплаты нет» независимо от окна: новый период не закрывает
старый. Каждая запись — только в одном блоке; оплаченные, отменённые и архивные не
просрочены. Формулировка не утверждает, что сервис отключён или что оплаты точно не было.
Месяц без года код разрешает сам: для предстоящих оплат (unpaid/all) — ближайший такой
месяц, включая текущий; для истории (paid) — последний такой месяц, включая текущий;
явный год сохраняется; для covered год не угадывается (текущий). Баланс с расходом 0 —
«списание остановлено», не «срок неизвестен». Обычный /payments остаётся полным обзором. Эти фильтры пока относятся к payments;
неподдерживаемые фильтры других запросов требуют уточнения.

## Формирование сводок

Перед сводками различать текущую оплату и историю: payment_status=covered показывает
активные сервисы с текущим оплаченным сроком и соответствующие оплаченные календарные
периоды. «Что оплачено?» относится к covered; «что оплатил/когда платил» — к paid.
Архивные записи не попадают в текущий статус, но сохраняются в истории с явной пометкой.
Для календарных платежей covered не выводит покрытие: показывается «оплата за <период>
отмечена» (номинальный и ближайший следующий срок) отдельным блоком «Отмеченные календарные
оплаты», без «оплачено по дату». Блок «Сейчас оплачено» — только coverage с сохранённым
coverage_until, дата включительная. Границы покрытия квартального/годового платежа не
придумываются.
Обычные разговорные реплики маршрутизируются в kind=conversation и ограниченный intent
greeting/thanks/frustration/capabilities/acknowledgement. Это ответ без мутации и без
повторного финансового списка; цифры или фактические утверждения модель не генерирует.

Agenda/report payload собирает код: сроки, status, days_left estimate, last payment,
last correction, delivery history. На MVP числовые факты выводятся детерминированными
шаблонами. LLM может выбирать ограниченные tone snippets по IDs/категориям или писать
нефактическую вводную; не доверять свободному пересказу сумм/дат. Это сохраняет характер
без сложного «проверяющего агента». Без LLM весь report имеет template fallback.

## Лимиты и отказ

Intent timeout 20 секунд; максимум один retry на transient failure без повторной
mutation; output limit; дневной call cap configurable (default 50). Сохранять token
usage и модель, не весь приватный prompt в logs. Никаких provider calls каждый tick.
Стоимость показывать только по заданному тарифу/usage, иначе «оценка недоступна».
При отказе: «Не разобрал сообщение; данные не менял. Можно воспользоваться формой».
Не помечать неисполненный intent успешным. Независимые reminders работают.

## Prompt и схема: согласованность (live eval 583e757, 19/21)

- План («что у меня на неделе / сегодня») — `query.kind=agenda`; он сам охватывает просроченное,
  сегодня и ближайшие 7 дней, поэтому его `period` и `payment_status` всегда `all`. Фильтры
  периода и статуса принадлежат только payments-запросам (контракт отвергает иначе). Поля
  в strict-схеме обязательны, поэтому prompt прямо требует `all` для agenda и balance.
- «все X / оба X / каждый X» при нескольких подходящих кандидатах — решение владельца, а не
  неоднозначность: по одному действию на кандидата, preview покажет код. Уточнение — только
  если текст не говорит «все/оба».
- Ясная команда (действие со всем нужным, например «завтра позвонить маме») применяется как
  есть: kind=actions. Подтверждающее уточнение («Создать …?») на неё запрещено; вопрос — только
  при недостающих или неоднозначных данных (live eval ce0490c, A04-tomorrow).
- Подтверждено live eval на SHA `d87e1885197523fec34ee7bf56df8c83edb9691f`: prompt
  `intent-v5-clear-command`, gpt-6-luna, reasoning none, полный корпус 25/25, 26 API attempts
  (один встроенный повтор в `A09-until-january`), 123885 input / 2191 output tokens. Прежние
  прогоны: 583e757 — 19/21 (prompt v3), ce0490c — 22/23 (prompt v4).
- Версия prompt: `intent-v6-ty-style`. Тест сверяет, что prompt упоминает все значения
  period/payment_status из схемы и прямо запрещает период на agenda/balance.

## Диагностика eval

Отчёт `xboct eval` по каждому сценарию содержит `diagnostics` (только синтетический корпус,
в БД и логи приложения не попадает): очертание предложения (вид, типы действий и их цели
по названиям, фильтры запроса, вид разговорной реплики), текст уточнения и кандидаты, при
отказе — конкретные ошибки валидации (где, тип, сообщение; без самих значений) и вид
ошибки провайдера. Сырые аргументы вызова, заголовки и ключи в отчёт не попадают.
`xboct eval --only id1,id2` запускает подмножество корпуса.

## Стиль диалога: «ты»

Владелец задал стиль: только на «ты», без «пожалуйста» и формального «Вы», реплики короткие и
естественные, без канцелярита. «Кот» допустимо, но не в каждом сообщении. Образцы для
уточнений: «Уточни…», «Выбери…», «Укажи…».

- Относится к собственным словам ХВОСТа: уточнениям модели, фиксированным ответам, уведомлениям,
  подсказкам интерфейса. Названия, заметки, цитаты и другие сохранённые данные не меняются и не
  «исправляются»; глобальной подмены строк нет.
- Prompt `intent-v6-ty-style` содержит правило и прямо защищает текст владельца.
- `xboct.style.formal_markers` только находит нарушения (пожалуйста, вы/вам/вас/ваш*,
  множественное число повелительного -ите/-йте/-ьте), текст в «кавычках» пропускает. Его
  используют тест `test_style.py` (ни одна фиксированная фраза в коде, шаблонах и JS не
  формальная) и eval: любое уточнение и кейсы с `expect.ty_style` проверяются по стилю.
- Корпус: `demo-which`, `demo-which-top-up` (уточнение между двумя «Demo»),
  `own-words-stay-as-written` («вы» и «пожалуйста» в названии дела остаются как есть); всего 28.
  Fixture-eval проверяет корпус и конвейер, а не модель: стиль настоящих уточнений проверит live.

## Создание подписки и платежа из текста (`create_obligation`)

Диалог владельца про Demo показал пробел: действия `create_obligation` в контракте модели не было,
модель задавала «подтверждающие» уточнения, а «Да» нечего было подтверждать. Теперь:

- `ProposedAction` содержит `create_obligation` для `kind=coverage` (подписка, оплаченный период) и
  `kind=calendar` (платёж по календарю с правилом повтора и известной опорной датой). Баланс VPS
  через текст не создаётся: его заводят в форме (модель отвечает коротким уточнением-пояснением).
- Поля: `title`, `kind`, `amount` (как сказано), `currency` (RUB/USD/EUR только если названа),
  `price_period` (день/неделя/месяц/год — цена, а не повтор), `paid_through`, `paid_period`,
  `recurrence`, `first_payment_on`, `aliases`, `note`, `allow_duplicate`.
- **Граница оплаты считается кодом.** `paid_through` — `last_paid_day` («оплачено по X
  включительно»), `first_unpaid_day`, `unclear` («оплачено до X»), `month_only` («до января»).
  Код вычисляет `coverage_until = last_paid_day + 1 день`; модель границу не вычисляет. `unclear`
  и `month_only` — вопрос кода, ничего не создаётся.
- **Известное начало и срок оплаты (`paid_period`).** «Купил 10 октября на месяц» — это начало
  и длительность именно оплаченного периода (`start` + `length`: day/week/month/year). Код
  считает конец календарными месяцами (`extend_coverage`: 31 января + 1 месяц → 28/29 февраля,
  переход года), модель конец не считает. Правила: начало и срок известны → preview без вопроса,
  `coverage_until` — первый неоплаченный день (он же следующий срок оплаты); явно названная
  граница сохраняется; граница и период, не совпадающие друг с другом, — один конкретный вопрос
  (`paid_period_conflict`); период, который уже закончился до сегодняшнего дня, — вопрос
  «продлевали ли с тех пор» (`paid_period_elapsed`), а не молчаливо просроченная запись.
  Цена и «продлевается каждый месяц» не создают второй срок и не переопределяют границу, названную
  раньше в диалоге (правило в prompt v8). Периодичность цены сама по себе («17 долларов в месяц»), дата первой оплаты и «продлевается
  каждый месяц» покрытия не доказывают: остаётся вопрос `paid_through_missing` (с напоминанием,
  что известна лишь дата первой оплаты). `Payment` и дата фактического списания не создаются.
  Preview показывает оплаченную границу, «следующая оплата с …» и строку заметки «Оплачено с …
  на … , по … включительно». Правило будущего продления как отдельное поле не хранится
  (у подписки нет правила повтора; хранение потребовало бы изменения схемы — предложение
  вынесено на разбор): срок следующей оплаты виден и по нему идут напоминания.
- **Создание всегда проходит через сохранённый preview** (`PendingIntent`), текст которого строит
  код из типизированной команды. Preview сохраняется в той же транзакции, что и текст с просьбой
  подтвердить. «Да»/«Нет» относятся к текущему сохранённому preview; повтор доставки «Да»
  отвечает по квитанции и не создаёт вторую запись. Модель не пишет вопросов «Создать …?».
- **Короткие «Да»/«Нет» решает код, а не выбор `kind` моделью.** Однозначные ответы из
  закрытого списка («да», «подтверждаю», «верно», «нет», «не надо», «отмена» и т. п., без
  регистра и знаков) обрабатываются до вызова модели по состоянию сохранённого плана: есть
  действующий — подтверждается/отменяется он; нет — честный ответ по последнему состоянию
  («Сохранённого предложения нет», «Предложение устарело», «Предложение уже отменено»,
  «Предыдущее предложение заменено и не действует», «Это предложение уже применено»).
  Разговорные реплики («ок», «давай», «да, но в долларах») по-прежнему идут в модель, которая
  не может подтвердить то, чего нет в плане. Повтор доставки отвечает по квитанции. В eval такой
  шаг помечен `route: code`, модель не вызывается (токенов и попыток нет), проверка ломается,
  если модель всё же вызвана.
- **Нерешённый вопрос снимает старый план.** Если новая попытка (действия или уточнение модели)
  закончилась уточнением, текущий сохранённый preview помечается заменённым в той же транзакции,
  что и квитанция: следующее «Да» не выбирает дату и не применяет старую операцию. Информационный
  запрос и разговор план не трогают; отклонённое некорректное предложение тоже.
- **«Да» без preview:** «Сохранённого предложения нет. Напиши, что добавить.»; после истечения
  (30 минут): «Предложение устарело. Напиши, что добавить, ещё раз.». Произвольное уточнение
  никогда не превращается в действие.
- **Недостающие факты спрашивает код** (стиль «ты»): сумма без валюты — «Уточни валюту: …»;
  подписка без границы — «До какого дня «…» уже оплачена? …»; календарный платёж без даты —
  «Назови ближайший срок платежа «…» и как часто он повторяется.». Нет суммы — не выдумывается и
  валюта не требуется. Дату первой оплаты для подписки с известной границей не требуют.
- **Что не теряется без миграции:** цена и период («Цена: 17 $ в месяц») и названная дата первой
  оплаты («Первая оплата: 10 октября 2026 (со слов владельца)») попадают в заметку строками,
  сформированными кодом; заметка владельца остаётся первой и без изменений. Записи об оплате
  (`Payment`) не создаются, preview говорит об этом.
- **Дубли:** активная запись с тем же названием/алиасом (или названием, продолженным словом) не
  дублируется молча: ответ ««X» уже есть (…). Создать вторую запись или изменить существующую?».
  Вторая запись — только при явной просьбе (`allow_duplicate`), существующая не меняется;
  в preview это видно («уже есть — по твоей просьбе создаю вторую запись»). Политика хранится в
  подтверждаемой команде (`CreateObligation.duplicates`: `forbid`/`allow`; формы — `unchecked`)
  и проверяется в транзакции применения: запись, появившаяся между preview и «Да» (в том числе
  по алиасу), или два одинаковых создания в одной пачке дают `stale_preview` — вся группа не
  применяется, предложение остаётся неподтверждённым. Два одинаковых названия в одном запросе без
  просьбы о второй записи код спрашивает ещё до preview (`duplicate_in_request`).
